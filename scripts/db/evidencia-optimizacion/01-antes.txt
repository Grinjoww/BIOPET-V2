CONSULTA CRÍTICA ELEGIDA
------------------------
Endpoint real:      GET /api/citas?page=0&size=20&sort=fechaHora,desc
Rol que la dispara:  ROLE_ADMIN / ROLE_VETERINARIO / ROLE_AUXILIAR (vista global
                     de citas — la que usa el frontend por defecto al abrir la
                     pantalla "Citas": ver cita-api.service.ts, listar() usa
                     sort='fechaHora,desc' como valor por defecto).
Controller:          CitaController.listar(Pageable, UserDetails)
Service:             CitaService.listar(...) -> para estos 3 roles llama a
                     CitaRepository.findAllByActivoTrue(pageable)
Repository:          CitaRepository (Spring Data derived query)
Tabla:               citas (400.000 filas, 384.266 con activo=true)
Filtro:              activo = true (selectividad ~96 %: casi ninguna fila se
                     descarta, por eso idx_citas_activo YA EXISTE pero el
                     planificador nunca lo usa — no aporta nada con esa
                     selectividad).
Ordenamiento:        fecha_hora DESC (pedido explícito del frontend).
Índices existentes en citas ANTES de esta fase:
    citas_pkey             btree (id)
    idx_citas_activo       btree (activo)      <- existe, NO se usa en el plan
    idx_citas_mascota      btree (mascota_id)
    idx_citas_veterinario  btree (veterinario_id)
Ningún índice cubre fecha_hora.

SQL EXACTO capturado con spring.jpa.show-sql=true contra el endpoint real
(Hibernate 6, generado tal cual, sin editar):

    SELECT c1_0.id, c1_0.activo, c1_0.actualizado_en, c1_0.creado_en,
           c1_0.estado, c1_0.fecha_hora, c1_0.mascota_id, c1_0.motivo,
           c1_0.veterinario_id
    FROM public.citas c1_0
    WHERE c1_0.activo
    ORDER BY c1_0.fecha_hora DESC
    FETCH FIRST 20 ROWS ONLY;

Consulta de conteo que Spring Data ejecuta en la MISMA petición (para
Page.totalElements):

    SELECT count(c1_0.id) FROM public.citas c1_0 WHERE c1_0.activo;

NOTA IMPORTANTE (para no exagerar la mejora más adelante):
  El COUNT necesita tocar TODAS las filas que cumplen activo=true sin importar
  el orden — ningún índice sobre fecha_hora puede acelerar este COUNT. Se
  documenta aquí para que el "antes/después" del reporte final sea honesto:
  la mejora del índice aplica al SELECT principal (el que ordena y pagina),
  NO a este conteo.

LATENCIA TOTAL DE LA PETICIÓN (SELECT + COUNT, página 0):
  65.401 ms + 56.221 ms ≈ 121.6 ms de trabajo en PostgreSQL, más
  deserialización JPA, el N+1 real de mascota/veterinario por fila (ver
  hallazgo de la sección 5) y serialización JSON — coherente con los ~153 ms
  de extremo a extremo medidos en la verificación end-to-end de una fase
  anterior de este mismo proyecto.
